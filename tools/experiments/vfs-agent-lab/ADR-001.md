# ADR-001 — Developer-only agent fixture VFS (2026-10-16)

Status: **proposed / implemented as an isolated experiment; NOT production-approved**. Owner: KARETA experiment lane PR #135. Related issues: #136–#140.

## Decision and boundaries

Use experimental Node.js 26 `node:vfs` **only in the development/test lab**, with a separate `MemoryProvider`-backed workspace per *logical* agent task. Ingestion and result export use fixed, bounded JSON documents; no direct access to application DB, PHP APIs, user content or production. Node.js 22 remains the primary application-gates runtime, and KARETA's production stack remains PHP/JS/MySQL.

This VFS is **not a sandbox**. Agent responses are untrusted text, never code that is executed, imported or given paths. Use operating-system/container/process boundaries for any future untrusted execution. VFS `unmount()` removes the mount view, not the RAM consumed by a still-referenced VFS instance; do not promise deterministic memory reclamation or secure erasure.

### In scope (this experiment)

1. Synthetic fixture documents for `diagnostic`, `crm`, `verifier` logical roles.
2. Separate in-memory file trees; fixed `/inbox/task.json` and `/outbox/result.json` accessors.
3. Maximum **64 KiB per JSON document**; strictly validated short agent identifiers.
4. Node 26 + `--experimental-vfs` tests for positive and rejection paths and mounted `node:fs` behavior.
5. A *later* opt-in local Ollama adapter using one in-flight request, explicit model name, bounded response/timeout, no model pulls.

### Out of scope

- Executing agent-generated JS/Python/shell; plugins, `eval`, `Function`, dynamic `import` of model output.
- Cloud requests; fetching new models automatically; remote Ollama URLs; uncontrolled network access.
- Actual VIN, customer data, identity session, passwords, production DB records or live repair recommendations.
- Public route, REST API, SPA, Android/WebView bridge, `s.kareta.kz` staging or production deployment.
- Authentication or authorization features: this lab cannot grant any KARETA app capability.
- Persistance: no disk storage or schema migration is introduced.

## Threat model

Trusted operators and code invoke the lab; fixture documents and model text are **untrusted input**. Threats: path traversal, excessive memory/prompt payloads, oversized model output, infinite waits, localhost-to-external redirects, accidental live-data export, executing returned code, conflating fixture success with actual QA evidence.

Mitigations: no free-form path API, JSON-only inputs, bounded sizes, explicit task/model allowlists in later stages, timeout/abort on inference, `redirect: 'error'`, explicit loopback network target, reject unexpected response shape and error statuses, never interpolate model output into code/commands. VFS alone does not prevent memory pressure, accessing host files from trusted code or a compromised Node process.

## Resource budget / compatibility

One task at a time initially. Cap serialized fixture input and result to 64 KiB each. Ollama adapter follow-up budget: e.g. 8 KiB input, 64 KiB response, 1 concurrent request, 60 s timeout, small `num_ctx` and `num_predict` cap, `keep_alive: 0` unless profiling justifies otherwise. These are *code-level input/request* limits, **not** guaranteed RAM/VRAM consumption ceilings for the model. Do not run an expensive model on a constrained workstation without hardware/runtime capacity check.

Node `node:vfs` is experimental and requires `--experimental-vfs`; production Node 22 application CI and PHP run unchanged.

## Acceptance / gates

1. PR diff restricted to `tools/experiments/vfs-agent-lab/**`, dedicated VFS CI, and this ADR.
2. CI for **exact candidate HEAD**: Node 26 VFS fixture syntax, negative tests, mount/unmount, demo = PASS.
3. Existing application checks on exact candidate = PASS, no shared-contract changes.
4. Independent reviewer checks source/diff, documents risks, flags any gaps; neither green CI nor ADR counts as a code security audit.
5. Model integration only on a separately reviewable PR, mock tests first. Local Ollama runtime smoke may be NOT RUN until a real configured local Ollama is available; never promote it to PASS.
6. Always report DESIRED / IMPLEMENTED / VERIFIED / DEPLOYED separately. Deployment remains **NOT RUN and prohibited** for this stage.
