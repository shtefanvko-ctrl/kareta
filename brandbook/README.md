# KARETA.KZ Brandbook

Рабочая папка брендбука и дизайн-канона KARETA.KZ.

## Источники истины

При конфликте решений действует следующий приоритет:

1. `css/next/design_contract.css` — общий технический дизайн-контракт и канонические shared tokens.
2. Ролевые foundation-файлы (`css/next/master_ui_foundation.css` и аналоги) — семантические токены роли и компоненты.
3. Route/surface contracts — только геометрия/bridge конкретной поверхности; не должны переопределять общий бренд без явного решения.
4. `brandbook/CANON.md` — брендовые правила, назначение токенов и применение на Web/PWA/Android/iOS/SMM.
5. `brandbook/archive/` — исторические материалы; не источник runtime-решений.

## Канонический логотип

Полный логотип приложения берётся из Git:

`assets/logo/main/kareta_logo_full.png`

Иконка приложения:

`assets/onboarding/kareta_logo_icon.png`

Геометрия логотипа неизменяема: знак автомобиля/ключа, вертикальный разделитель, KARETA.KZ, подпись «АВТОСЕРВИС».

## Главное правило

Brandbook не вводит второй набор runtime-токенов. Он документирует и расширяет существующий Git-канон. Если брендбук и runtime расходятся, сначала фиксируется решение в каноне, затем синхронно обновляются документация и код.

## Состав

- `CANON.md` — рабочий Brand & Design Canon.
- `tokens.css` — документирующий слой брендовых/semantic tokens, согласованный с Git-контрактом.
- `CHANGELOG.md` — изменения брендбука.
- `archive/Brand_Design_Canon_v1.md` — исходный v1 до reconciliation с Git.
- `exports/` — только экспортные артефакты; источником истины не являются.

## DoD изменения брендбука

Изменение считается готовым, когда:
- не меняет утверждённую геометрию логотипа;
- не создаёт параллельный набор токенов;
- проверено против `design_contract.css`;
- применимо минимум к mobile + desktop;
- для UI-решений указан semantic token/компонент;
- нет скрытого role-specific override, который ломает общий канон.
