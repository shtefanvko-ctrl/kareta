## DB migrations и schema policy

Текущий baseline использует `api/migration_manifest.php` версии **129** и ожидает ровно **129** последовательных migration-файлов с SHA-256 checksums.

Важно: `.84.xx` — номер application release, а `001…129` — номер DB migration. Они независимы.

Поздний migration block, присутствующий в baseline:

- 077–089 — Identity context/API/domain ownership/realtime/CRM/marketplace/migration engine/auth/capability/legacy bridge/production readiness.
- 090–103 — context-members hotfix, schema startup recovery, Smart Action Hub, Master navigation preferences, STO workflow, admin operations, universal dashboard, operational navigation/workspaces, onboarding/session/security/person-profile repair.
- 104–109 — Master order lifecycle, aftercare/finance/inventory, payroll/receivables, client exchange scale, dispatch engine, master profile runtime repair.
- 110–129 — works/reviews/wall, service pricing, Parts/Used/Seller, Master requests/exchange/orders/capacity/tariffs/shifts/recovery/STO command center, Master first-entry onboarding и Client first-entry state.

### Production migration rules

- Runtime DB migration в production fail-closed.
- Для разрешённого maintenance migration window требуется явный `KARETA_DB_RUNTIME_MIGRATION_WINDOW=1`.
- Migration manifest/checksums должны пройти release gate до deployment.
- Messaging schema не должна auto-create в production: `KARETA_MESSAGING_AUTO_SCHEMA` / `messaging_auto_schema` по умолчанию `false`.
- Messaging schema устанавливается отдельной явной командой: `php tools/messaging_schema_install.php`.
- `config.private.php` и provider credentials не входят в release package.

## Known limitations / operational notes

1. **Commissioning OTP.** В текущем baseline production commissioning bridge по умолчанию включает temporary static OTP `0000`, пока `KARETA_OTP_TEMP_STATIC_ENABLED=0` не задан явно. При отключении режим возвращается в fail-closed webhook transport.
2. **Messaging providers.** Telegram/WhatsApp требуют server-side credentials/webhook configuration. Секреты не сериализуются во frontend.
3. **Feature readiness.** Production feature matrix Stage 8 классифицирует часть сложных domains как BETA/INTERNAL/DISABLED; наличие route не означает READY.
4. **Staging infrastructure.** На момент сборки release note `s.kareta.kz` продолжает отдавать HTTP 403 на корне. Предыдущие проверки также зафиксировали отсутствующие FULL assets и устаревший `sw.js` на staging. Это environment/deployment blocker, а не основание считать code baseline невалидным.
5. **84.90 documentation gap.** В source baseline нет отдельного patch/recovery документа для `.84.90`; изменения не были искусственно реконструированы.
6. **84.97 historical note.** Recovery note фиксировал manifest parity 129 и отдельно указывал, что предполагаемые migrations 130–133 не входят в baseline.

## Rollback notes

### Application-only rollback

1. Сохранить текущий document root/полный rootless package и SHA-256.
2. Развернуть предыдущий проверенный application package атомарно.
3. Сохранить текущий server-side `config.private.php`; не заменять его файлом из архива.
4. Проверить parity `inc/asset_version.php ↔ sw.js`.
5. Обновить/инвалидировать Service Worker/cache только после успешного smoke.
6. Выполнить release checklist и основные auth/API/request/Master smoke checks.

### Database rollback

В текущем manifest нет общего release-wide `down`/reverse migration contract. Поэтому безопасный DB rollback — **restore из заранее сделанного MySQL snapshot/backup**, а не запуск старого migration manifest поверх новой schema.

Перед DB-affecting deployment обязательно:

- backup/snapshot БД;
- сохранить текущую migration version/checksums;
- проверить maintenance window;
- не удалять новые columns/tables автоматически при application rollback;
- если старый application code несовместим с новой schema, восстанавливать согласованную пару **application + DB snapshot**.

### Messaging rollback

- Остановить worker/cron перед откатом schema/provider config.
- Не удалять provider secrets.
- При возврате к версии без Messaging Core отключить webhook delivery/provider flags до завершения rollback.
- Messaging schema rollback выполнять только через DB snapshot/ручной согласованный SQL, не через runtime auto-schema.

## Pre-release / post-release checklist

Перед deployment:

- `bash tools/release_checklist.sh`;
- migration manifest version/checksum = 129/129;
- backup DB + document root + private config;
- проверить OTP mode и messaging provider flags;
- staging должен перестать возвращать 403;
- FULL assets должны отдавать 200 с корректным MIME.

После deployment:

- проверить `sw.js` и current release token;
- auth/session/context smoke;
- request create/edit/send;
- Master home/exchange/schedule/services;
- provider detail;
- chats/realtime;
- PWA manifest/service worker;
- error logging/error codes;
- rollback point хранить до завершения smoke.
