# KARETA.KZ — дополнение к утверждённому Landing Canon v2

**Тип:** приложение к существующему брендбуку, а не новый самостоятельный брендбук. **Слайды:** 13–27 из `KARETA_KZ_brandbook_landing_canon_v2_EXTENDED.pptx`. **Дата дополнения:** 06.11.2026. **Внедрение в действующий сайт:** не выполнено. Этот документ не заменяет `landing/styles.css`, `css/next/design_contract.css` и другие runtime-файлы.

## 1. Иерархия источников и неизменяемые положения

1. **Утверждённый Landing Canon v2**, исходные 12 слайдов: настоящий полноформатный логотип `assets/logo/main/kareta_logo_full.png`; пиктограмма автомобиля с ключом; белый фон; сервисный оранжевый `#FC6606`; графит `#474747`; подложка `#F7F7F5`. Логотип и первые 12 слайдов расширенного PPTX сохранены, не перерисованы.
2. Текст первоисточника доступен агентам в [`LANDING_CANON_V2_SOURCE.md`](LANDING_CANON_V2_SOURCE.md). Визуал исходника и новое дополнение доступны в проектной библиотеке `/kareta.kz/docs/design/`; PDF/PPTX там же.
3. Старый продуктовый брендбук v1 из 40 слайдов содержит полезные правила UI, ролей, карты, WCAG и адаптивности. Синий `#2563EB` из v1 **не является** заменой главного фирменного оранжевого цвета в исправленном v2.
4. Действующие CSS и `KaretaUIIcons` остаются источниками реализации, а не поводом вводить новый шрифт, логотип, роутер, слои, БД или независимую CSS-тему. Конфликт runtime с брендбуком оформляется как migration gap и исправляется отдельно.
5. Не менять рабочую шапку, нижнее меню, мобильные отступы, позиционирование модальных окон, Identity-context и протокол OTP при добавлении визуальных компонентов.

## 2. Главная проблема проекта: design drift и повторные наложения

Обнаруженные отличия исходников и канона:

| Источник | Текущее значение | Канон / вывод |
| --- | --- | --- |
| `landing/styles.css` | `--orange:#ff6500` | брендовый первоисточник `#FC6606`, миграция отдельным PR |
| `css/next/icon_standard.css` | `--k-icon-accent:var(--k-orange,#ff6b00)` | fallback расходится с `#FC6606`; не заменять вслепую |
| `css/next/design_contract.css` | `--k-text:#111827; --k-surface-page:#f5f6f8` | не равно brand graphite / soft, роль токена нужно разграничить |
| UI onboarding / screenshots | тёмные варианты, многослойные карточки | это эскизы, а не разрешение менять белый landing-канон |
| стили master, client, shell | несколько owner-файлов и postlude | риск конфликтов `z-index`, `overflow`, `position:fixed` и повторных override |

**Первопричина, которую должен устранять агент:** у одних и тех же элементов нет однозначного владельца стилей и семантического источника цвета. Нельзя каждый раз исправлять переполнение дополнительным глобальным CSS-пластырем. Надо найти реальный owner и выполнить проверку соседних экранов, иначе симптомы повторяются.

## 4. Математика сочетаемости / WCAG 2.2

Для каждого sRGB-канала `c` из `0..1`: `f(c)=c/12.92`, если `c<=0.04045`, иначе `f(c)=((c+0.055)/1.055)^2.4`. `L=0.2126R+0.7152G+0.0722B`. Контраст `CR=(Lmax+0.05)/(Lmin+0.05)`. Расчёты — по точным 8-битным HEX, а не по ощущениям.

| Пара fg / bg | Коэффициент | Применение |
| --- | ---: | --- |
| белый `#FFFFFF` / оранжевый `#FC6606` | **2.982:1** | FAIL для обычного белого текста на CTA |
| белый `#FFFFFF` / затемнённый orange `#B84902` | **5.261:1** | PASS WCAG AA, светлая CTA |
| тёмный `#0B1220` / оранжевый `#FC6606` | **6.279:1** | PASS WCAG AA, тёмная CTA |
| графит `#474747` / белый `#FFFFFF` | **9.291:1** | PASS, фирменный текст |
| secondary `#667085` / soft `#F7F7F5` | **4.638:1** | PASS AA, вторичный текст |
| исходный жёлтый `#F59E0B` / белый | **2.148:1** | FAIL для обычного текста/иконок |
| исходный циан `#06B6D4` / белый | **2.428:1** | FAIL для обычного текста/иконок |

**Нормы:** текст обычного размера минимум `4.5:1`, крупный текст `3:1`, значимые нетекстовые компоненты и границы `3:1`. Оригинальный брендовый логотип не перекрашиваем: логотипы исключены из требований контраста текста WCAG 1.4.3. Цвет не должен быть единственным сигналом выбора/ошибки (1.4.1). WCAG 2.2 2.5.8 устанавливает целевой размер указателя 24×24 CSS px *с исключениями*, а рекомендация KARETA для мобильных — 44–48 px.

Полные машинно-вычисленные файлы: [`contrast_matrix_v2_addendum.csv`](contrast_matrix_v2_addendum.csv) (все пары), [`contrast_pairs_v2_addendum.csv`](contrast_pairs_v2_addendum.csv) (роль и состояния), [`canon_v2_addendum_tokens.json`](canon_v2_addendum_tokens.json) (происхождение и семантика).

## 5. Цветовая гармония и степень её доказуемости

Оттенки для текста и состояний получены сохранением HSL Hue/Saturation и изменением Lightness бинарным поиском до контраста >=5.25:1 для эталонного фона. Отдельный файл [`hue_compatibility_v2_addendum.csv`](hue_compatibility_v2_addendum.csv) даёт HSL hue (градусы) и минимальную разницу углов до brand-orange. Это **измеряемое цветовое родство**, а не научное доказательство того, что дизайн визуально красив. Итог зависит от занимаемой площади, подписей, плотности и реального фона, поэтому требует UX-review и просмотра на телефоне.

| Семантика | Исходный | Для обычного текста на white | Контраст / white | Для тёмной карточки |
| --- | --- | --- | ---: | --- |
| брендовый акцент | `#FC6606` | `#B84902` | 5.261 | `#FC6606` |
| успех | `#16A34A` | `#117C39` | 5.295 | `#17A84C` |
| ошибка | `#DC2626` | `#D22222` | 5.260 | `#E76B6B` |
| предупреждение | `#F59E0B` | `#966006` | 5.286 | `#F59E0B` |
| гео/OBD | `#06B6D4` | `#04768A` | 5.298 | `#06B6D4` |

**Контроль:** если фон semi-transparent / image-backed / gradient, вычислять цвет уже после alpha-compositing. Не объявлять PASS по исходному HEX на сложном фоне. Тон яркого брендового orange на белом поле нельзя использовать как единственный важный 3:1 контур/значок, хотя это логотипная окраска.

## 6. SVG-иконки — дописываем каталог, не заменяем библиотеку

Существующие источники: `js/next/ui_icons.js` (`KaretaUIIcons`); `assets/icons/tabler/` (`Tabler v3.48.0 MIT`, спрайт, индекс, лицензия); `css/next/icon_standard.css`. Они первичны для действующего интерфейса. Четыре дополнительных опциональных SVG в `assets/icons/kareta/` иллюстрируют направления регистрации: `client`, `auto-service`, `auto-services`, `auto-goods`. Они **ещё не подключены к экранам**.

SVG-контракт: `viewBox 0 0 24 24`, `stroke=currentColor`, `fill=none`, `stroke-width=1.9`, округлые окончания, оптически единый рисунок; 16/18/22/28 px видимый размер; минимум 44–48 px касательная зона продукта; один `iconId` на понятие; текстовая подпись обязательна. Не добавлять жёсткий оранжевый в path, не копировать логотипы марок/СТО, не хранить скрипты, удалённые ссылки и `foreignObject` внутри SVG. Для light UI применять контрастный цвет линии по фактической поверхности, а не автоматически raw `#FC6606`.

## 7. Регистрация и вход — дизайнерский слой, не переписывание Identity

Первый экран обсуждаемой концепции: `Клиент`, `Автосервис`, `Автоуслуги`, `Автотовары`. Возможен мультивыбор направлений бизнеса после определения/подтверждения Account/Person и Identity Context; клиенту не нужно выдавать три отдельных аккаунта. Старый маршрут и OTP, авторизация и RBAC не меняются от самих карточек дизайна; новую архитектуру контекстов должен отдельно согласовать backend. Не переносить концепт в production только из-за иллюстраций.

## 8. Стабилизатор дизайна / не повторять прошлые ошибки

Перед любой правкой страницы:

- открыть `AGENTS.md`, `ai/CONTEXT_ROUTER.md`, `ai/rules/design-system.md`, этот документ и 12 исходных страниц; затем изучить текущие owner-файлы CSS/JS и затронутые соседние маршруты;
- проверить что CSS регулирует только один владелец для header / nav / fixed / shell; запретить новые глобальные `!important` и переписывание геометрии для маскировки симптомов;
- экраны: 320, 390, 768, 1366, 1440, 1920 CSS px; без горизонтального скролла, наложений, отрезанного контента; проверить 200% zoom, RU/KK/EN, длинные значения и server-error состояния;
- проверять safe-area и нижнее меню мобильного клиента и мастера, размер карточек, `min-width:0`, модальные окна, focus-visible, управление клавиатурой и блокировку скролла под модалкой;
- проверять ссылку `icon ID → имеющийся SVG`, состояния `selected / disabled / hover / focus / error`; отсутствие иконки — **FAIL**, не «не замечено»;
- не трогать продукты, роли, API, DB, сессии, маршруты и PHP ради цветового исправления;
- правила release: IMPLEMENT → ISOLATED TEST → QA → review/approval → deploy/verify. Никаких `PASS`/«в проде» без фактических тестов точного SHA.
