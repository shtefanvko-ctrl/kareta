# KARETA · безопасные заявки на предварительные карточки СТО

Дата: 2026-11-04. Ветка: `feat/sto-directory-owner-claim-20261104`.
Режим: **ISOLATED_CANDIDATE / PRODUCTION DENY**. Это не релиз и не активированные учётные записи действующих организаций.

## Цель и пределы

Собирать карточки реальных СТО только из разрешённых открытых сведений, показывать их в отдельном справочнике с отметкой **«Аккаунт не активирован»**, дать владельцу KARETA-профиля отправить заявку с доказательством, вручную подтвердить владельца и привязать **право на карточку** к проверенному `account_id`.

Кандидат никогда не получает мастерский `user_id`, `sto_profiles.active=1`, `service_offers`, выдуманные оценки, цены, свободные слоты или чат. Не публиковать персональные сведения и фотографии сотрудников, не создавать отзывы или заявки от имени реальных людей.

## Контракты и ограничения

- Схема: `tools/sto_claim_schema.sql` (3 изолированные таблицы); `directory_visible=0` по умолчанию. Идентификатор и fingerprint должны быть стабильными, адрес и источник обязательными. Внешний импорт проверяется вручную перед `directory_visible=1`.
- GET `api/sto_claims.php?action=list&city=...`: только `directory_visible=1` и статусы `unclaimed/activated`, с `canBook=false`, `canChat=false`, без поддельных рейтингов. Другие роли и штатные каталоги не меняются.
- POST JSON c `X-Kareta-Claim-Request: 1`: `action=submit`, `review`, `activate`, `saveDraft`. Дополнительно общий серверный same-origin guard. Никаких OTP/ролей/телефонов из параметров запроса.
- `submit`: подлинная Identity-сессия, активный аккаунт, подтверждение полномочий, метод и референс; идемпотентность, 3 заявки в сутки, 7-дневный cooldown после отклонения.
- `review`: подтверждённый администратор, **не заявитель**, независимый метод и референс, проверка возможных дублей в `sto_profiles`, эксклюзивное одобрение с блокировкой остальных заявок.
- `activate`: только ранее одобренный `account_id` и явное подтверждение. Меняет `sto_directory_candidates.status` на `activated`. Не создаёт `organizations`, `organization_members`, `sto_profiles`, не выдаёт полномочия.
- `saveDraft`: только владелец подтверждённой карточки, только описание справочника; не включает публикацию предложений и запись.

### Критический RBAC-gate

В текущем Identity Core `organization.owner` содержит capability `*` (обнаружено в изолированной базе `kareta_m_staging` 2026-11-04); много legacy-роутов не всегда передают явный resource scope. Выдача членства `owner` или создание связанного legacy-STO может приводить к эскалации доступа. Поэтому текущий этап **намеренно не создаёт рабочий кабинет СТО**. Перед разрешением полного доступа необходимо закрыть и независимо проверить RBAC-gate (#167), ограничения конкретной организации, сценарии чужой записи и администрирования.

### Миграции и интеграция

В текущем `origin/main` активные `api/migration_manifest.php/json` зарегистрированы только до **137**, при наличии незарегистрированных файлов 138–144. Есть открытые PR #155 (guard дрейфа) и PR с версиями миграций 145–146. Не добавлять собственный номер миграции и не обновлять манифест до согласованного разрешения конфликтов. **Не выполнять SQL на production**.

Только после разрешения дрейфа и одобрения:
1. Назначить уникальную миграцию и включить её checksum в оба канонических манифеста; прогнать migration integrity.
2. Применить DDL в изолированной базе, затем импортировать проверенные карточки с проверкой дублей MySQL. По умолчанию публичная видимость выключена.
3. Подтвердить авторизованные OTP/Identity E2E: неавторизованный, чужой claimant, повторные и параллельные заявки, self-approve, независимая проверка, владелец, чужой аккаунт; проверить доступ к admin API и чужим СТО.
4. Запустить Playwright/Chromium мобильный/ПК, регрессии мастеров и СТО, manifest + asset loader; затем QA и отдельное разрешение на production.
5. Резервная копия и rollback: отключение входа на `sto_claims.php` и lazy asset, `directory_visible=0` (без удаления уже сохранённых заявок), не затрагивая `users/organizations/sto_profiles`.
