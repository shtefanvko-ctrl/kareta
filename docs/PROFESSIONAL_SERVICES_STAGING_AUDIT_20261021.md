## Ограничения и оставшиеся риски

- Браузерный тест выполнен с имитацией данных мастера; живой вход мастером, публикация предложения и сквозная запись клиента ещё **не проверены**.
- На staging при аудите был 1 профиль мастера, 0 СТО, 0 заказов. Невозможно заявить о проверенной маршрутизации реальных исполнителей.
- Публичный список мастеров всё ещё нуждается в поиске по точному `serviceId` и реально подтверждённым `service_offers`; базовый текстовый поиск по профессии сам по себе недостаточен.
- Не проверены совместимость услуг с VIN/типом транспорта, реальные квалификации и правомочность HV-работ. Все связи с оборудованием — рекомендации.
- В текущей рабочей копии staging было более 120 иных незакоммиченных изменений; **не делать** общий `git reset/checkout/pull`, массовую синхронизацию, импорт через старую `kareta_service_catalog_import()` без отдельно проверенного контракта.
- Клиентские демонстрационные скидки и формулировки о свободном времени требуют отдельной привязки к реальным предложениям; этот пакет их не трогал.

## Продолжение

1. Подтвердить фактический staging snapshot всех runtime-файлов и зафиксировать отдельный release patch без переноса чужих dirty-файлов.
2. Испытать через авторизованного мастера сохранение цены, длительности и статуса услуги; убедиться, что его существующий профиль не сбрасывается.
3. Добавить фильтрацию мастеров и СТО через опубликованный `service_offers.service_id` с параметрами автомобиля и города.
4. Провести сквозной e2e: услуга → доступный исполнитель → слот → заявка → заказ, убедившись, что услуга нигде не теряется.
5. После тестов оставить изменения только на staging до отдельного решения по prod.

**Правило отката:** не удалять новые работы при наличии заказов/предложений, связанных с ними. При необходимости остановить видимость новых услуг отдельным обратимым переключателем; не заменять всю базу резервной копией без оценки новых данных.
