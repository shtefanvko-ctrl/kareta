# KARETA staging — связка услуга → исполнитель → запись

Дата: 2026-10-21. Цель: безопасное внедрение на `s.kareta.kz`. Продакшн не менялся.

## Что фактически внедрено

1. Новый публичный read-only endpoint `GET /api/catalog/masters_by_service.php?serviceId=...` принимает также `type` (`master`, `sto`, `all`), `search`, `city`.
2. Выдача включает только исполнителей с **собственными** предложениями `service_offers` с точным `service_id`, `active=1`, `booking_enabled=1`, `moderation_status='approved'`, `availability_status='available'`, действующим публичным профилем. Платформенные предложения не считаются реальными мастерами. Для СТО сохранены требования к названию, городу и адресу.
3. `js/next/pages/details.js`: переход из карточки услуги в каталог мастеров содержит `serviceId`, затем он сохраняется в ссылке записи мастера или профиле СТО и клиентском prefill. Отсутствующий/снятый оффер блокирует выбор другой услуги.
4. `js/next/pages/masters.js`: общий поиск не затронут. По `serviceId` включается строгий endpoint. Если никого нет, пользователю сообщается об отсутствии опубликованных исполнителей, а не показывается случайный мастер.
5. `api/catalog/service_catalog.php`: новые активные предложения профессиональных работ `pro_*` нельзя опубликовать с продолжительностью менее 5 минут или с нулевой фиксированной ценой; цена `agreement` допускается. Старые услуги не меняются.
6. Никакого автоматического присвоения квалификаций, услуг или оборудования мастерам, никаких фиктивных цен и свободных окон.

## Ограничения и следующие проверки

- Пока зарегистрированные мастера и СТО не создадут собственные опубликованные предложения, строгий поиск по новым операциям будет честно возвращать пустой список. На момент аудита все 109 исходных `service_offers` принадлежали платформе.
- Браузерные e2e-сценарии используют фикстуры; требуются реальная авторизованная сессия мастера, сохранение предложения, подбор с клиентского аккаунта, проверка доступного слота и создание тестовой заявки с откатом.
- Совместимость автомобиля, квалификация и оборудование не были проверены независимым экспертом и остаются рекомендательными.
- В staging-worktree параллельно работают другие участники. PR #144 остаётся draft и не должен массово заменять живой staging или сливаться в prod без сравнительного аудита, отдельного release asset-bump и полного регрессионного тестирования.
- Канонические хедер, нижнее меню и CSS в этом пакете не изменялись.
