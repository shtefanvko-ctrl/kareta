## Цель

Работать с папкой `Анализ/` в три обязательных прохода. Нельзя переносить исследовательские гипотезы в runtime только потому, что они структурно валидны.

## Источники истины

При конфликте использовать порядок:
1. текущее решение пользователя;
2. AGENTS.md / Definition of Done / verification gates;
3. исполнимый код и exact-SHA evidence;
4. runtime/staging evidence;
5. актуальный план;
6. PR/issue;
7. старые документы `Анализ/`.

Всегда отдельно писать состояния: DESIRED / IMPLEMENTED / VERIFIED / DEPLOYED.

## Проход 1 — ДОПОЛНИТЬ АНАЛИЗ

1. Прочитать весь релевантный `Анализ/data`, `Анализ/evidence`, README, реестр ошибок и текущие runtime-каталоги.
2. Для каждой сущности отметить:
   - research source;
   - runtime source;
   - ID/cross-reference status;
   - expert status;
   - measurement status;
   - может ли она влиять на production.
3. Дополнить пробелы, не меняя статус гипотез на «проверено».
4. Отдельно сохранять:
   - оборудование;
   - профессии;
   - service relations;
   - поисковые формулировки/уточнения;
   - рынок/цены;
   - ошибки и evidence gaps.
5. Не копировать существующий service catalog и не создавать второй source of truth.

## Проход 2 — ПОВТОРНО ПРОВЕРИТЬ И ДОПОЛНИТЬ

Перед любым runtime-изменением повторно сверить результат с текущим `main` и активными PR.

Обязательно:
- получить текущий main SHA;
- проверить `ai/CHANGE_LANES.md`;
- проверить открытые PR на те же shared contracts;
- сверить asset/runtime registry, API actions, route wiring и существующие tests;
- перепроверить старые E01–E15 и пометить каждую запись CURRENT / CLOSED / SUPERSEDED / NOT_RUN;
- найти новое расхождение, появившееся после первой инвентаризации;
- не считать наличие файла доказательством рабочего runtime.

Если за время работы main изменился, повторить сверку до интеграции.

## Проход 3 — ВНЕДРИТЬ МИНИМАЛЬНЫЙ ДОКАЗУЕМЫЙ ИНКРЕМЕНТ

Правила:
- использовать существующую change lane;
- не создавать конкурирующий router/API/catalog/identity source;
- research relations сначала только advisory/read-only;
- профессия не включает услуги автоматически;
- оборудование не означает квалификацию;
- `need_buy` не означает доступ;
- M3 matching не включать до отдельного проверяемого контракта;
- никаких Android/DB migration/deploy изменений без отдельной необходимости.

После кода:
1. syntax/static;
2. focused unit/contract;
3. application gate;
4. runtime/API/DB, если доступно;
5. browser/device;
6. deployment/provenance — только когда это входит в DoD.
